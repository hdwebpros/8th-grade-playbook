# The Seam — Play Data ⇄ Diagram Design Contract

This document settles §9 of HANDOFF.md: the play-data schema and the diagram's
visual design, negotiated together, fixed before implementation. Every agent
building on either side of this seam follows it. The canonical machine-readable
half lives in `app/types/football.ts` — this document explains the *why* and
carries the visual half.

Design authority: Fable (orchestrator). Football authority: the varsity scans
in `reference/varsity/` and §4 of HANDOFF.md. Where they seem to conflict,
football wins and the design flexes.

---

## 1. Coordinate system: yards, not pixels

All positions and paths in play data are expressed in **yards** on a field
coordinate system:

- `x` — lateral. `0` is the ball. Positive = offense's **right** (viewer's
  right; offense always drawn at the bottom facing up).
- `y` — depth. `0` is the line of scrimmage. Positive = downfield into the
  defense. Negative = the offensive backfield.

Why: yard coordinates make the data football-true (a 4-yard split is a 4-yard
split), make **mirroring a pure transform** (negate `x`), and leave every
pixel decision — scale, crop, padding, aspect — to the renderer. Data contains
**zero** pixels, colors, or styling. The renderer auto-fits the viewport to
the bounding box of all players and paths plus padding; typical Veer diagrams
land around x ∈ [−16, 16], y ∈ [−7, 10].

## 2. The schema (canonical: `app/types/football.ts`)

Shape summary — read the types file for exact fields:

- **`Formation`** — 11 players (`X Y L R S Q C LG RG LT RT`), each with a
  yard position. Red, Black, (later Split Wide).
- **`Front`** — a named defensive look (`44`, `43`, `52`) as a list of
  defenders: stable `id` (e.g. `E-L`, `N`, `B-R`), display `label`
  (`E T N B W S C F $`), yard position. 4-4 and 4-3 are *even* fronts, 5-2 is
  *odd* — the varsity rules ("Even: RIP … Odd: SCOOP") key off this
  `scheme` field.
- **`Play`** — one play in one direction (`veer-red` and `veer-black` are two
  `Play` objects; the second is generated by the mirror helper and corrected
  where football isn't symmetric). Carries:
  - `assignments` — the front-independent teaching table, per player. This is
    the single source for the play page's assignment panel, the quiz, and the
    PDF table. Two registers per entry: `rule` (short, kid-facing, keeps
    varsity terms like *Rip*, *Scoop*, *Base*) and `detail` (coaching points).
  - `vs` — per-front plan (`FrontPlan`): a **complete** per-player action map
    for that front, plus assignment-text overrides where the front changes the
    job, plus the `readKey` (defender id) for option plays, plus optional
    `ignored` (defender ids the scheme deliberately leaves unblocked — e.g.
    the men the option handles). Reuse across fronts happens with TS spreads
    in the data files, not in the schema.
- **`Action`** — a semantic, typed movement: `kind` ∈
  `carry | run | route | block | motion | pitch | fake`, a path of yard
  points, optional `targetId` (a defender id). **Semantics in, styling out**:
  the renderer alone decides how a block looks vs a motion. A `block` with a
  `targetId` and no path is legal — the renderer draws from the player to the
  defender and caps it with the block bar, so front changes never strand a
  hand-authored path.
- **`RouteDef`** — the ten numbered routes, each a path from a receiver
  origin at `(0,0)`.

### Position labeling (presentation ruling)

Data is keyed by **actual player** (`LT`, `RG`, `Y`, `R` …), never by
playside/backside role — a `Play` knows its `direction`, so the UI computes
and shows a *playside/backside* badge next to the plain label. A 13-year-old
reads "LG — you're playside" instead of decoding `PSG`, but hears the varsity
vocabulary in the same breath, which is the bridge §4 asks for. Transcription
must resolve varsity's `PST/PSG/BSG/BST/PSW/BSW` rows to actual players per
direction and must not let the relabeling change any job.

### Mirroring

`mirrorPlay` / `mirrorFormation` in `app/utils/mirror.ts`: negate every `x`,
swap side-suffixed ids (`LT↔RT`, `LG↔RG`, `E-L↔E-R`, …), leave everything
else. Authors write one direction from the scans, generate the other, then
**diff against the scan of the mirrored version** (varsity p6 shows both
directions) and hand-correct any asymmetry. Corrections live in the data file,
stated as overrides on the generated object, so intent is visible.

## 3. Diagram visual language (fixed — renderer implements exactly this)

The diagram is a **pure SVG** component. No canvas, no raster: it must be
crisp on a phone, in a projected quiz, and in print.

**Field.** Quiet stage, not a stadium simulation. Background is the theme's
field color. The LOS is the strongest line on the field (2px, full width,
`--dg-los`). Faint 1-yard hash ticks along the LOS and a single faint line 5
yards downfield give depth scale without noise. Nothing else.

**Offense.** Circles, radius ≈ 0.55 yd, `--dg-player-fill` fill with 2.5px
`--dg-player-stroke` stroke; the **center is a square** (football
convention). Position letter set in the display font, bold, centered. The
**ball carrier** fills `--dg-accent` (Wolves red) with white letter. The QB
gets a double stroke ring. On `highlight`, the selected player and his
actions render full strength and everything else drops to 35% opacity —
this single mechanic powers know-your-job quiz reveals and the play page's
tap-a-player interaction.

**Defense.** No circles — bare letters (`E T N B W S C F $`) in
`--dg-defense`, same size as offensive letters, 600 weight. Visually "them":
present, legible, unmarked. The **read key** defender gets a `--dg-accent`
dashed ring plus a small `READ` caption — the one defensive callout the
option game needs. Defenders in a plan's `ignored` list get a smaller
`--dg-defense` dashed ring, no caption — "nobody blocks him on purpose";
the read key never doubles up (its READ ring already says it).

**Paths.** All paths smoothed (Catmull-Rom → cubic Bézier), round caps:

| kind    | stroke                                            | end cap |
| ------- | ------------------------------------------------- | ------- |
| `carry` | 3.5px `--dg-accent`                               | arrowhead |
| `run`   | 2.25px `--dg-line`                                | arrowhead |
| `route` | 2.25px `--dg-line`                                | arrowhead |
| `block` | 2.25px `--dg-line`                                | **T-bar** (perpendicular, 0.9 yd wide) |
| `motion`| 2.25px `--dg-line`, dashed 6 4                    | none (flows into next action) |
| `pitch` | 2px `--dg-accent`, dotted 1 5                     | small arrowhead |
| `fake`  | 2px `--dg-line` at 40% opacity                    | arrowhead |

Arrowheads are compact filled triangles, not marker-huge. A player's actions
render in array order and chain start-to-end.

**Themes.** All colors come from CSS custom properties so one renderer serves
both worlds. Dark app theme (default): field `#10141A`, lines `#E8EAED`,
defense `#8A939E`, accent `#D6202F`, player fill `#10141A`/stroke `#E8EAED`.
Print theme (`theme="print"`): field white, lines near-black `#111`, defense
`#555`, accent stays red (one-color pop on paper), player fill white/stroke
`#111`. The component sets fallback values for every `--dg-*` var so it
renders correctly before/without the app shell's stylesheet.

**Interaction.** `interactive` prop enables tap targets (min 44px hit area
regardless of visual radius) on offensive players; component emits
`select(pos | null)`. Assignment text renders **outside** the SVG (the page
owns that panel) — the diagram never draws text bubbles that would fight a
375px viewport.

### Component contracts

```vue
<PlayDiagram
  :play="play"            <!-- Play -->
  :front="'44'"           <!-- FrontId -->
  :formation="formation"  <!-- Formation (resolved by page from play.formation) -->
  :fronts="fronts"        <!-- Record<FrontId, Front> -->
  :highlight="posId"      <!-- OffPosId | null -->
  :interactive="true"
  :theme="'app' | 'print'"
  @select="pos => ..."
/>
<RouteTreeDiagram :routes="routes" :highlight="num | null" :theme="..." @select="num => ..." />
```

Both components size to container width (viewBox + `width:100%`), no fixed px.

## 4. Design tokens (app-wide)

Set in `app/assets/css/tokens.css` by the shell; the values are decided:

- **Palette.** `--red: #D6202F` (sampled from the mark), `--red-deep: #9E1420`,
  `--ink: #0B0D10`, `--field: #10141A`, `--panel: #171C23`,
  `--chalk: #E8EAED`, `--steel: #8A939E`, `--line: #232A33`. Dark-first app
  (film-room feel, easy on a bus at night); print is light.
- **Type.** Display: **Barlow Condensed** (600/700, uppercase for headings and
  jersey-style labels — athletic block without costume). Body/UI: **Barlow**
  (400/500/600). Both via `@nuxt/fonts`. Diagram letters use Barlow Condensed 700.
- **Icons.** Lucide (`@iconify-json/lucide`, already installed) via
  `<Icon name="lucide:...">`.
- **Shape & motion.** Radius 10px cards / 8px controls; motion is fast and
  small (120–200ms ease-out, translate/fade only), `prefers-reduced-motion`
  respected. No parallax, no scroll hijack.

## 5. Why the schema looks like this (the negotiation record)

- **Typed actions, not styled strokes** — the design keeps full freedom to
  restyle every play at once; authors can never make one diagram "special".
  This is the direct answer to how the varsity book decayed.
- **Block-by-target** — 60 diagrams × 3 fronts means alignments will shift;
  aiming blocks at defender ids instead of coordinates keeps diagrams correct
  when a front is tuned once, globally.
- **Per-front complete action maps** — the renderer stays dumb (no rule
  engine deciding what RIP means); football logic lives in data where a coach
  can audit it. Sharing between fronts is a TS spread, visible in the diff.
- **Assignments as first-class text per player** — one source feeds the play
  page, the know-your-job quiz, and the PDF table; they can never drift.
- **Yard coordinates + mirror transform** — halves the authoring load for the
  full book (~60 → ~30 hand-authored diagrams) without a lossy abstraction,
  because corrections after mirroring are explicit overrides.

## 6. File ownership (phase 1)

- `app/types/football.ts` — **frozen** (orchestrator). Changes require the
